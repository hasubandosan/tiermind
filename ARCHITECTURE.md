## 1. Что это за проект

Социальная платформа самопознания и сравнения вкусов (псевдоаналог personality-database.com).
Три столпа, один общий каркас:

1. **Тесты** — научно обоснованные (приоритет) + развлекательные (с честной пометкой).
2. **Предпочтения** — что юзер любит/оценивает в разных сферах (музыка, игры, кино, еда...).
3. **Тир-листы** — вложенные (элемент тир-листа может сам быть тир-листом).

Социальный слой: профили, поиск юзеров, друзья, **группы сравнения** (друзья сравнивают
результаты тестов, предпочтения и тир-листы).

### Ключевая идея объединения
Не три приложения, а **один каталог сущностей (items)** + три «представления» над ним:
- тир-лист = расставленные items по тирам,
- предпочтение = оценка/отметка item'а,
- тест = источник «черт» профиля.

Всё сводится в **профиль** и сравнивается в **группах**.

## 2. Принципы

1. **Бесплатно.** Только free-tier сервисы. Не вводить платные зависимости без явного ОК владельца.
2. **Просто.** Минимум движущихся частей. Если можно без отдельного бэкенд-сервера — без него.
3. **Безопасность на уровне БД** (Row Level Security), а не «надеемся, что фронт не обманет».
4. **Научность честно.** У каждого теста есть метка: `scientific` / `entertainment` и источник.
5. **Маленькие PR.** Одна задача — одна ветка — один PR.
6. **Не ломать main.** Всё через ветки и PR.

## 3. Стек (бесплатный)

| Слой | Выбор | Зачем / ограничения free-tier |
|---|---|---|
| Фронтенд | **Vite + React + TypeScript + Tailwind** (SPA) | Проще Next.js, меньше шансов, что ИИ-боты что-то сломают |
| Хостинг фронта | **Cloudflare Pages** | Бесплатно, деплой при пуше в GitHub |
| БД + Auth | **Supabase** (Postgres + Auth + RLS) | Free: ~500 МБ БД. Проект «засыпает» после ~1 недели неактивности → см. §11 |
| Файлы/картинки | **Cloudflare R2** (позже) | Бесплатный лимит хранилища; на MVP можно без картинок/по URL |
| Серверная логика | **Supabase Edge Functions** или **Cloudflare Workers** (только если нужно) | На MVP — не нужна, считаем на клиенте/в SQL |
| Drag & drop | `@dnd-kit` | Для тир-листов |
| Роутинг/данные | `react-router`, `@supabase/supabase-js`, `@tanstack/react-query` | |
| CI | **GitHub Actions** | Проверка сборки на каждом PR |

**Почему Supabase, а не Render+Neon:** Supabase даёт БД + авторизацию + права доступа в одном месте,
не нужно писать и хостить свой бэкенд. Render free-сервисы «засыпают» и долго просыпаются.
Neon — только БД, auth пришлось бы делать самим.

**Секреты:** `.env` НИКОГДА не коммитить. Публичные ключи (`VITE_SUPABASE_URL`,
`VITE_SUPABASE_ANON_KEY`) задаются в настройках Cloudflare Pages. `service_role` ключ — не в репо и не во фронте.

## 5. Модель данных (Postgres)

Все таблицы с включённым **RLS**. `auth.users` — встроенная таблица Supabase.

### Профили и социальное
- `profiles` — `id (=auth.users.id)`, `username (unique)`, `display_name`, `bio`, `avatar_url`, `visibility` (`public|friends|private`)
- `friendships` — `id`, `requester_id`, `addressee_id`, `status (pending|accepted|blocked)`, `created_at`
- `groups` — `id`, `owner_id`, `name`, `created_at`
- `group_members` — `group_id`, `user_id`, `role`, `status (invited|joined)`

### Каталог (общий для тир-листов и предпочтений)
- `categories` — `id`, `slug`, `name` (music, games, movies, food, ...)
- `items` — `id`, `category_id`, `title`, `image_url`, `meta jsonb`, `created_by`, `is_verified`

### Предпочтения
- `preferences` — `user_id`, `item_id`, `rating` (1–10 или like/dislike — решить в §12), `note`, `updated_at`
  (PK: `user_id + item_id`)

### Тир-листы (вложенные)
- `tierlists` — `id`, `owner_id`, `title`, `category_id`, `parent_item_id NULL`, `visibility`, `created_at`
- `tiers` — `id`, `tierlist_id`, `label` (S/A/B...), `color`, `position`
- `tierlist_entries` — `id`, `tierlist_id`, `tier_id`, `item_id`, `position`,
  `child_tierlist_id NULL` ← **вложенность**: запись может вести в другой тир-лист

> Вложенность = у записи есть `child_tierlist_id`. Пример: тир-лист «Игры» → запись «Dark Souls» →
> дочерний тир-лист «Боссы Dark Souls». Защита от циклов — триггер/проверка при вставке.

### Тесты
- `tests` — `id`, `slug`, `title`, `kind (scientific|entertainment)`, `version`, `source`, `license`, `description`
  (сами вопросы лежат в `content/tests/*.json`, в БД — только метаданные и версия)
- `test_results` — `id`, `user_id`, `test_id`, `test_version`, `answers jsonb`, `scores jsonb`, `taken_at`, `visibility`

### Сравнение
Вычисляется на лету (view/функция), отдельных таблиц не нужно на MVP:
- по тестам — расстояние между векторами черт (напр. Big Five),
- по предпочтениям — совпадения и корреляция оценок по общим items,
- по тир-листам — корреляция рангов (Spearman) по общим items.

## 6. Тесты: политика содержания

**Научные (приоритет, свободные лицензии):**
- **Big Five** на основе **IPIP** (International Personality Item Pool — public domain). Версии: Mini-IPIP (20), IPIP-NEO-120.
- **HEXACO** — *проверить лицензию перед использованием* (бесплатно для исследований, коммерция/публичные сервисы — уточнить).
- Другие открытые шкалы из IPIP (напр. ценности, стили принятия решений) — только с подтверждённым источником.

**Не включать в MVP:** клинические/диагностические опросники (депрессия, тревога и т.п.) — этически и юридически рискованно.

**Развлекательные:** «16 типов», эннеаграмма, «какой ты персонаж» и т.п.
- Обязательная плашка «развлекательный, не научный».
- **Не использовать название/товарный знак «MBTI»** (зарегистрированная марка) — называть «16 типов (по Юнгу)» / «типология в стиле MBTI».

**Формат теста** (`content/tests/<slug>.json`): `slug, title, kind, version, source, license, scale, items[{id, text, trait, reverse}], scoring, interpretation[]`.
Подсчёт баллов — чистая функция в коде, покрыта тестами.

Каждый результат хранит `test_version`, чтобы старые результаты оставались корректными при обновлении теста.

## 7. Приватность и безопасность

- По умолчанию результаты тестов — **приватные**; юзер сам решает: `public | friends | private`.
- Сравнение в группе показывает только то, чем участник **согласился** поделиться.
- RLS-политики — часть миграций, проверяются при каждом PR, затрагивающем таблицы.
- Предупреждение в UI: результаты тестов — не диагноз.
- Удаление аккаунта удаляет все его данные (каскад).

## 8. Рабочий процесс (владелец не кодит)

**Роли:** владелец = мержит PR через GitHub-интерфейс. ИИ = пишет код и даёт команды.

**Формат ответа ИИ-бота на каждую задачу:**
1. Что делаем (2–3 строки) и какие файлы затронуты.
2. Команды для терминала (копипаст-блок), в этом порядке:
   ```bash
   git checkout main && git pull
   git checkout -b feat/<короткое-имя>
   # применить патч:
   git apply <<'EOF'
   ...diff...
   EOF
   git add -A
   git commit -m "feat: <описание>"
   git push -u origin feat/<короткое-имя>
   ```
3. Что проверить (1–3 пункта: «открой страницу X, должно быть Y»).
4. «Теперь создай PR и смержи в GitHub».
5. Обновить §9 и §10 этого файла (отдельным патчем или в том же PR).

**Правила:**
- Именование веток: `feat/…`, `fix/…`, `docs/…`, `db/…`.
- Коммиты: `feat:`, `fix:`, `docs:`, `db:`, `chore:`.
- Миграции БД — новый файл `supabase/migrations/NNNN_описание.sql`, старые НЕ править.
  Применение миграции владелец делает по инструкции бота (вставка SQL в Supabase → SQL Editor, либо `supabase db push`).
- Если патч не применяется — не гадать: попросить владельца прислать вывод `git status` и ошибку.
- Если задача неоднозначна — сначала задать ОДИН уточняющий вопрос.
- Не менять стек и структуру без записи в §12 (Решения) и согласия владельца.
