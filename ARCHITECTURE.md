## 1. Что это за проект

Социальная платформа самопознания и сравнения вкусов (псевдоаналог personality-database.com).
Три столпа, один общий каркас:

1. **Тесты** — научно обоснованные (приоритет) + развлекательные (с честной пометкой).
2. **Предпочтения** — что юзер любит/оценивает в разных сферах (музыка, игры, кино, еда...).
3. **Тир-листы** — вложенные (элемент тир-листа может сам быть тир-листом).

Социальный слой: профили, поиск юзеров, друзья, **группы сравнения** (друзья сравнивают
результаты тестов, предпочтения и тир-листы).

### Ключевая идея объединения
Не три приложения, а **один каталог сущностей (items)** + три «представления» над ним:
- тир-лист = расставленные items по тирам,
- предпочтение = оценка/отметка item'а,
- тест = источник «черт» профиля.

Всё сводится в **профиль** и сравнивается в **группах**.

## 2. Принципы

1. **Бесплатно.** Только free-tier сервисы. Не вводить платные зависимости без явного ОК владельца.
2. **Просто.** Минимум движущихся частей. Если можно без отдельного бэкенд-сервера — без него.
3. **Безопасность на уровне БД** (Row Level Security), а не «надеемся, что фронт не обманет».
4. **Научность честно.** У каждого теста есть метка: `scientific` / `entertainment` и источник.
5. **Маленькие PR.** Одна задача — одна ветка — один PR.
6. **Не ломать main.** Всё через ветки и PR.

## 3. Стек (бесплатный)

| Слой | Выбор | Зачем / ограничения free-tier |
|---|---|---|
| Фронтенд | **Vite + React + TypeScript + Tailwind** (SPA) | Проще Next.js, меньше шансов, что ИИ-боты что-то сломают |
| Хостинг фронта | **Cloudflare Pages** | Бесплатно, деплой при пуше в GitHub |
| БД + Auth | **Supabase** (Postgres + Auth + RLS) | Free: ~500 МБ БД. Проект «засыпает» после ~1 недели неактивности → см. §11 |
| Файлы/картинки | **Supabase Storage** (бакет `item-images`) | Free: ~1 ГБ. Картинки уменьшаются в браузере до 512 px (JPEG), лимит файла 512 КБ. Если не хватит — перейти на Cloudflare R2 |
| Серверная логика | **Supabase Edge Functions** или **Cloudflare Workers** (только если нужно) | На MVP — не нужна, считаем на клиенте/в SQL |
| Drag & drop | `@dnd-kit` | Для тир-листов |
| Роутинг/данные | `react-router`, `@supabase/supabase-js`, `@tanstack/react-query` | |
| CI | **GitHub Actions** | Проверка сборки на каждом PR |

**Почему Supabase, а не Render+Neon:** Supabase даёт БД + авторизацию + права доступа в одном месте,
не нужно писать и хостить свой бэкенд. Render free-сервисы «засыпают» и долго просыпаются.
Neon — только БД, auth пришлось бы делать самим.

**Секреты:** `.env` НИКОГДА не коммитить. Публичные ключи (`VITE_SUPABASE_URL`,
`VITE_SUPABASE_ANON_KEY`) задаются в настройках Cloudflare Pages. `service_role` ключ — не в репо и не во фронте.

## 5. Модель данных (Postgres)

Все таблицы с включённым **RLS**. `auth.users` — встроенная таблица Supabase.

### Профили и социальное
- `profiles` — `id (=auth.users.id)`, `username (unique)`, `display_name`, `bio`, `avatar_url`, `visibility` (`public|friends|private`)
- `friendships` — `id`, `requester_id`, `addressee_id`, `status (pending|accepted)`, `created_at` (одна связь на пару людей; блокировки — позже). Клиент может менять только `status`, и только принимая входящую заявку.
- RPC-функции (security definer, миграция `0003_friends.sql`): `are_friends(a,b)`, `my_friendships()`, `profile_card(username)`, `search_profiles(query)`. Клиент НЕ читает чужие профили таблицей напрямую для страниц людей, а ходит через эти функции.
- Группы сравнения — см. §5 «Группы сравнения» ниже (миграция `0006_groups.sql`).

### Каталог (общий для тир-листов и предпочтений) — миграция `0004_catalog_preferences.sql`
- `categories` — `id`, `slug`, `name`, `emoji`, `subtitle_label` (подпись поля «текст под названием»: «Вселенная», «Исполнитель или группа»...), `sort_order`.
  Набор категорий ведёт администратор через миграции (пользователи категории не создают). Сейчас: movies, series, anime, games, music, characters, books, food.
- `items` — `id`, `category_id`, `title` (1–120), `subtitle` (необязательно, 1–120), `image_url` (необязательно, только https), `created_by`, `created_at`, `updated_at`.
  Уникальность: (категория, название, подпись) без учёта регистра. Элементы создают сами пользователи (до 50 в сутки). Удаления нет.
  Автор может править элемент, пока его не оценил кто-то другой (`item_is_shared`; при появлении тир-листов добавить в проверку их записи).
- RPC `browse_items(category, query, limit, offset)` — каталог с поиском по названию/подписи и моей оценкой; `can_see_preferences(owner)`.

### Предпочтения
- `preferences` — `user_id`, `item_id`, `rating` smallint от −2 до 2 (**2 обожаю · 1 нравится · 0 нейтрально · −1 не нравится · −2 ненавижу**), `updated_at`. PK: `(user_id, item_id)`. Нет строки = не оценено.
- `profiles.preferences_visibility` (`private|friends|public`, по умолчанию `private`) — кто видит все предпочтения владельца.
- Шкала в коде: `features/catalog/types.ts` (`RATINGS`). Для сравнения людей удобна симметричная шкала вокруг нуля.

### Тир-листы (вложенные) — миграция `0005_tierlists.sql`
- `tierlists` — `id`, `owner_id`, `title` (1–120), `note` (≤300), `tags text[]` (≤10), `visibility` (`private|friends|public`, по умолчанию `private`), `created_at`, `updated_at`.
- `tiers` — `id`, `tierlist_id`, `label` (1–20), `color` (#rrggbb), `position`. Новый тир-лист получает тиры S A B C D E (цвета из старого проекта). До 20 тиров.
- `tierlist_entries` — `id`, `tierlist_id`, `tier_id` (**null = «банк»**, ещё не расставлено), `item_id` (элемент из общего каталога), `position`, `note` (≤300), `child_tierlist_id`. Один элемент — один раз в списке; до 500 записей в списке.
- **Вложенность:** `child_tierlist_id` ведёт во вложенный тир-лист. Правила (триггер): только свой тир-лист, у вложенного ровно один родитель, циклы запрещены. Удалили вложенный — ссылка обнуляется; удалили родителя — вложенные остаются самостоятельными корнями. Элемент «Геральт» → вложенный «Боссы Dark Souls» и т.д.
- Тир удалён → его записи уходят в конец банка. Тир обязан принадлежать тому же списку (составной внешний ключ).
- Видимость вложенных списков задаётся отдельно у каждого; если родитель виден, а вложенный скрыт — по ссылке откроется «скрыт».
- RPC: `create_tierlist`, `create_child_tierlist(entry)`, `move_entry(entry, tier, index)` (атомарно переставляет и перенумеровывает), `reorder_tiers`, `list_tierlists(owner)`, `tierlist_ancestors(id)`; помощники `owns_tierlist`, `can_view_tierlist`.
- Клиентская логика перетаскивания (`features/tierlists/layout.ts`: `computeMove`, `applyMove`) повторяет серверную `move_entry`; тесты сверяют результаты на одном сценарии. Менять надо ОБА места.

### Тесты
Вопросы, шкалы и метаданные тестов НЕ в БД, а в `apps/web/src/content/tests/*.json` (версионируются в git).
- `test_results` — `id`, `user_id`, `test_slug`, `test_version`, `answers jsonb`, `scores jsonb`, `visibility`, `taken_at`
  (история попыток сохраняется; «текущий» результат = самый свежий по `taken_at`). Миграция `0002_test_results.sql`.

### Группы сравнения — миграция `0006_groups.sql`
- `groups` — `id`, `owner_id`, `name` (1–60), `created_at`. До 20 групп на владельца.
- `group_members` — `group_id`, `user_id`, `status (invited|joined)`, `share_tests`, `share_preferences` (обе по умолчанию `false`), `invited_by`. До 12 человек в группе.
- `group_tierlists` — `group_id`, `tierlist_id`, `user_id`: тир-листы, которые участник сам прикрепил к группе (до 10 на человека).
- **Приглашать может только владелец и только своих друзей.** Приглашённый видит название группы и владельца, но НЕ участников и данные, пока не примет приглашение. При принятии он сам выбирает, чем делиться (по умолчанию — ничем).
- **Согласие, а не ослабление приватности.** Данные участников читаются только через RPC (`group_tests`, `group_preferences`, `group_tier_scores`, `group_members_view`, `my_groups`), и только участникам со статусом `joined`; обычные права на профиль/результаты/предпочтения/тир-листы не меняются (прямой `select` чужих данных по-прежнему закрыт). Выход/удаление участника сразу убирает его данные из сравнения и откладывает прикреплённые тир-листы.
- Запись в таблицы групп клиенту запрещена — только RPC: `create_group`, `invite_to_group`, `respond_group_invite`, `update_group_sharing`, `leave_group`, `remove_group_member`, `set_group_tierlist`; владелец дополнительно может переименовать (`update groups set name`) и удалить группу.

### Сравнение (клиентский код `features/groups/compare.ts`, покрыт тестами)
Совпадение двух людей = `100 · (1 − средняя разница / максимально возможная разница)` по общим ключам:
- **тесты** — по `percents` результата (шкалы Big Five, полюса 16 типов, типы эннеаграммы), диапазон 100;
- **предпочтения** — по общим оценённым элементам, диапазон 4 (оценки −2…2), нужно ≥ 3 общих;
- **тир-листы** — верхний тир = 1, нижний = 0 (`group_tier_scores`), элемент в нескольких списках человека усредняется, нужно ≥ 3 общих.
Общий процент пары — среднее по доступным составляющим; если данных не хватает, составляющая не учитывается.
Те же формулы будут использоваться для сравнения прохождений шаблонов (M7).

### Шаблоны тир-листов (M7, спроектировано, ещё не реализовано)
Идея владельца: тир-листы создают любые люди **как шаблоны**, а проходят их и сами авторы, и другие люди.
- `tierlists.is_template boolean` — список можно «сделать шаблоном» в настройках. Шаблон = набор тиров (названия/цвета) + набор элементов из каталога + вложенные шаблоны; расстановка автора в шаблоне при прохождении не копируется.
- `tierlists.source_template_id` — у прохождения ссылка на исходный шаблон.
- RPC `start_from_template(template)` — создаёт **копию** для вызвавшего (его собственный приватный тир-лист): те же тиры, все элементы в банке; вложенные тир-листы копируются рекурсивно (ограничения по глубине и размеру). Шаблон потом могут менять — прохождения не затрагиваются. Можно проходить многократно; для сводок берётся последнее прохождение пользователя.
- Видимость шаблона как у обычных тир-листов: `public` попадает в галерею `/templates` (поиск, теги, сортировка по числу прохождений), `friends`/`private` — по правам.
- Результаты прохождений: прохождение остаётся приватным, пока автор сам не откроет его (`friends`/`public`). На странице шаблона: «сообщество» — средние оценки элементов по видимым вам прохождениям, список открытых прохождений, **сравнение с вашим прохождением и с автором** (формула из раздела «Сравнение»).
- Прохождение можно прикрепить к группе (M6) — тогда группа сравнивает расстановки одного и того же шаблона.
- Безопасность/модерация: лимит шаблонов на пользователя, жалоба на шаблон (позже), копирование не раскрывает чужие приватные данные (копируется только структура шаблона, который вам виден).
- Открытые вопросы для владельца: можно ли «форкнуть» чужой шаблон и править; нужны ли обложки; показывать ли счётчик прохождений публично.

## 6. Тесты: политика содержания

**Научные (приоритет, свободные лицензии):**
- **Big Five** на основе **IPIP** (International Personality Item Pool — public domain). Версии: Mini-IPIP (20), IPIP-NEO-120.
- **HEXACO** — *проверить лицензию перед использованием* (бесплатно для исследований, коммерция/публичные сервисы — уточнить).
- Другие открытые шкалы из IPIP (напр. ценности, стили принятия решений) — только с подтверждённым источником.

**Не включать в MVP:** клинические/диагностические опросники (депрессия, тревога и т.п.) — этически и юридически рискованно.

**Развлекательные:** «16 типов», эннеаграмма, «какой ты персонаж» и т.п.
- Обязательная плашка «развлекательный, не научный».
- **Не использовать название/товарный знак «MBTI»** (зарегистрированная марка) — называть «16 типов (по Юнгу)» / «типология в стиле MBTI».

**Формат теста** (`apps/web/src/content/tests/<slug>.json`, типы — `features/tests/types.ts`):
общие поля `slug, version, order, kind (scientific|entertainment), title, description, source, note, scaleMin, scaleMax, items[{id,text,scale,reverse}]`
+ поле `scoring` определяет остальное: `scales` (шкалы, проценты), `dichotomies` (пары полюсов → код типа + стек функций), `enneagram` (тип 1–9 + крыло).
Новый тест = новый JSON-файл (реестр подхватывает сам). Подсчёт — `features/tests/scoring.ts`, покрыт тестами (`npm test`).
**Правило `reverse`:** для шкал — согласие с пунктом означает НИЗКОЕ значение шкалы; для пар полюсов — согласие означает ВТОРОЙ полюс.
**Нельзя менять `id` вопросов** у выпущенных тестов; при изменении формулировок/ключей — повышать `version`.
Подсчёт баллов — чистая функция в коде, покрыта тестами.

Каждый результат хранит `test_version`, чтобы старые результаты оставались корректными при обновлении теста.

## 7. Приватность и безопасность

- По умолчанию результаты тестов — **приватные**; юзер сам решает: `public | friends | private`.
- Сравнение в группе показывает только то, чем участник **согласился** поделиться.
- RLS-политики — часть миграций, проверяются при каждом PR, затрагивающем таблицы.
- Предупреждение в UI: результаты тестов — не диагноз.
- Удаление аккаунта удаляет все его данные (каскад).
- **Видимость профиля:** `public` — виден всем и ищется; `friends` — ник и имя видны всем и ищутся (чтобы можно было отправить заявку), био и результаты — только друзьям; `private` — не ищется и не открывается никем, кроме владельца.
- **Видимость результата теста** задаётся отдельно для каждого результата (`private|friends|public`), по умолчанию `private`.
- Сырые ответы теста (`test_results.answers`) недоступны клиентам вообще (колоночные права): наружу отдаются только итоги.
- Поиск людей — только для вошедших, минимум 2 символа, максимум 20 результатов (защита от скрейпинга).
- Картинки элементов: только https-ссылки или файлы из бакета `item-images` (загрузка только в свою папку `<user_id>/`); браузер запрашивает их без Referer.
- Любая миграция, меняющая права/RLS, сопровождается сценарием в `supabase/tests/` (см. README там).

## 8. Рабочий процесс (владелец не кодит)

**Роли:** владелец = мержит PR через GitHub-интерфейс. ИИ = пишет код и даёт команды.

**Формат ответа ИИ-бота на каждую задачу:**
1. Что делаем (2–3 строки) и какие файлы затронуты.
2. Команды для терминала (копипаст-блок), в этом порядке:
   ```bash
   git checkout main && git pull
   git checkout -b feat/<короткое-имя>
   # применить патч:
   git apply <<'EOF'
   ...diff...
   EOF
   git add -A
   git commit -m "feat: <описание>"
   git push -u origin feat/<короткое-имя>
   ```
3. Что проверить (1–3 пункта: «открой страницу X, должно быть Y»).
4. «Теперь создай PR и смержи в GitHub».
5. Обновить §9 и §10 этого файла (отдельным патчем или в том же PR).

**Правила:**
- Именование веток: `feat/…`, `fix/…`, `docs/…`, `db/…`.
- Коммиты: `feat:`, `fix:`, `docs:`, `db:`, `chore:`.
- Миграции БД — новый файл `supabase/migrations/NNNN_описание.sql`, старые НЕ править.
  Применение миграции владелец делает по инструкции бота (вставка SQL в Supabase → SQL Editor, либо `supabase db push`).
- Если патч не применяется — не гадать: попросить владельца прислать вывод `git status` и ошибку.
- Если задача неоднозначна — сначала задать ОДИН уточняющий вопрос.
- Не менять стек и структуру без записи в §12 (Решения) и согласия владельца.

## 11. Известные ограничения и обходы

- **Supabase free «засыпает»** после ~недели без активности → добавить GitHub Actions cron-запрос раз в несколько дней (задача в M0).

- **Cloudflare Pages:** собирает только статику (SPA) — серверный рендеринг не нужен на MVP.
- Лимиты free-тарифов меняются — перед масштабированием перепроверять актуальные условия.

## 13. Унаследованный код (legacy) и план переноса

Два исходных прототипа. Решение: **не склеивать код**, а собрать новый проект на стеке из §3 и
**портировать** из старых проектов логику, данные тестов и дизайн. Старые проекты лежат в
`legacy/psycho_soc/` и `legacy/tierlists/` как справочник; после переноса удаляются.

### 13.1 psycho_soc (React 18 + Vite 5, JS, LocalStorage)
- **Есть:** 4 теста (OCEAN 10 вопросов, Dark Triad 27, MBTI-подобный 20, Эннеаграмма 18), класс `TestRunner` + по классу на тест,
  вопросы отдельно в `src/data/*.js`, радар-диаграмма и просмотр результатов в `App.jsx`, тёмная тема, экспорт/импорт профиля в JSON,
  идея «достоверности» результата (ручной ввод = 0%, тест = 100%, психолог = до 200%).
- **Не работает / заглушки:** вход через Google (в `main.jsx` стоит `YOUR_GOOGLE_CLIENT_ID`), вкладка «Поиск» (только placeholder),
  друзья и чат (только в планах). Всё хранится в LocalStorage браузера.
- **Gemini:** юзер вводит свой ключ, ответы теста уходят во внешний сервис. В новый проект НЕ переносим на этапе MVP.
- **Что переносим:** тексты вопросов и логику подсчёта → `content/tests/*.json` + чистые функции scoring; радар-диаграмму; тёмную тему; идею достоверности (как поле результата).
- **Что пересмотреть по научности (важно):**
  - OCEAN сделан по TIPI (10 пунктов) — это легитимный, но самый короткий инструмент; формулировки переписаны своими словами → помечать «краткая оценка». Для `scientific` позже добавить Mini-IPIP (20) / IPIP-NEO-120.
  - Dark Triad подписан «SD3», но формулировки 27 пунктов похожи на вольный пересказ, а не на оригинальные пункты SD3 → **сверить с оригиналом/источником**, иначе помечать `entertainment`.
  - «MBTI» (20 вопросов) и Эннеаграмма (18 вопросов) → `entertainment`; слово «MBTI» в названии заменить (торговая марка).
  - Утверждение «пройден тест = достоверность 100%» вводит в заблуждение → заменить на метку типа теста + длину теста.

### 13.2 tierslists (один `index.html`, ~2000 строк, vanilla JS, LocalStorage `tierLists3`)
- **Есть:** тир-листы, **вложенность уже реализована** (`item.subTierId` → другой тир-лист), настраиваемые тиры (название+цвет),
  drag&drop предметов, картинки по URL, заметки с подсказкой, теги, поиск/сортировка в галерее, хлебные крошки,
  **граф связей** между вложенными листами, экспорт/импорт JSON.
- **Формат данных старого приложения** (нужен для импортёра):
  ```
  { "tier_<id>": { name, note, tags[], tierConfig:[{label,color}],
                   items:[{ id, name, image, note, tier:<label|null>, subTierId:<tier_id|null> }] } }
  ```
- **Ограничения:** у каждого тир-листа свои предметы (нет общего каталога), нет пользователей и шаринга, весь код в одном файле.
- **Что переносим:** модель вложенности, UX drag&drop, граф, теги, заметки, стили → React-компоненты в `features/tierlists/`.
  Предметы получают ссылку на общий каталог `items` (§5); старые «ничьи» предметы при импорте создаются как items пользователя.

### 13.3 Совместимость и миграция данных
- Написать **импортёры** обоих старых JSON-форматов (профиль psycho_soc и экспорт tierslists) — чтобы существующие данные владельца не пропали.
- Отображение полей: `tier_<id>` → `tierlists`; `tierConfig` → `tiers`; `items[].tier` → `tierlist_entries.tier_id`; `subTierId` → `child_tierlist_id`.
- Результаты тестов старого формата (`rawScores`, `processedResult`) → `test_results.scores` с `test_version = "legacy-1"`.
